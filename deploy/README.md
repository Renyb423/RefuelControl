# Production deployment

The workflow builds and tests the Angular SPA on a GitHub-hosted runner, publishes `sha-<commit>` and `latest` tags to GHCR, and deploys the exact OCI digest produced by that build through a dedicated self-hosted runner on the home server. The server receives only `docker-compose.prod.yml` and `deploy.sh`; it never receives source code or a Dockerfile and never builds the image.

## Quick path

1. Configure the three repository Actions variables listed below.
2. Confirm that Docker Engine, the Compose plugin, Traefik, `proxy_net`, and `flock` already exist on the server.
3. Register a dedicated GitHub Actions runner with the `refuelcontrol-deploy` label and run it as a system service.
4. Ensure the runner service user can write `/home/olvin/PROYECTOS/DevOps/applications/refuel-control` and access Docker.
5. Authenticate that same service user to GHCR, then push to `main` or run **Deploy production** manually from `main`.
6. Confirm the digest-pinned image, OCI identity, container health, and public HTTPS responses.

## GitHub configuration

Set these repository **Actions variables**:

| Variable | Required value |
| --- | --- |
| `DEPLOY_PATH` | Exactly `/home/olvin/PROYECTOS/DevOps/applications/refuel-control`. The workflow rejects any other value. |
| `SUPABASE_URL` | Public Supabase project URL used at build time. |
| `SUPABASE_KEY` | Browser-safe anon or publishable key used at build time. Never use a `service_role` or secret key. |

No custom Actions secrets are required. `GITHUB_TOKEN` is created automatically for each workflow run and is used to publish and clean up the GHCR package. The legacy SSH variables and secret are no longer used and can be removed after the migration succeeds.

The Supabase URL and anon/publishable key are compiled into browser JavaScript and are therefore public by design. Row Level Security must protect the data.

## One-time server setup

The only additional server service is the official GitHub Actions Runner process, preferably managed by systemd. Do not add a runner or deployment service to Compose. Docker and Traefik already exist; the workflow creates or updates only the RefuelControl application service.

### Register the dedicated runner

1. Open **Repository Settings → Actions → Runners → New self-hosted runner**.
2. Select the server platform and run the exact download, configuration, and verification commands generated by GitHub.
3. Add the custom label `refuelcontrol-deploy` during registration. The workflow also requires the standard `self-hosted` and `linux` labels; it does not require an architecture label.
4. Use GitHub's generated service commands to install and start the runner as a systemd service. The service must run as the same user that can write `DEPLOY_PATH` and access the Docker daemon.
5. Keep this runner dedicated to this private repository. Do not enable this production workflow for pull requests or forks.

Docker daemon access is effectively root-equivalent. Limit repository administration and workflow write access accordingly, keep the repository private, and do not share this runner with untrusted repositories or jobs.

The runner needs outbound HTTPS on TCP port 443 to GitHub and GHCR. GitHub Actions does not require inbound SSH, port forwarding, or an Internet-exposed management port.

### Existing infrastructure

Traefik is an external stack that this pipeline does not create or modify. It must run Traefik v3 with the Docker provider, use `exposedByDefault=false`, and provide all of the following resources:

| Resource | Required value |
| --- | --- |
| Public domain | `refuelcontrol.fetek.es` |
| External Docker network | `proxy_net` |
| HTTPS entrypoint | `websecure` |
| Certificate resolver | `dev_resolver` |

Configure DNS `A` and `AAAA` records for `refuelcontrol.fetek.es` to point to the public addresses handled by Traefik. Traefik already owns the global HTTP-to-HTTPS redirect.

Verify that the pre-existing external network is available. The deployment checks it but never creates it:

```sh
docker network inspect proxy_net
```

The server must also provide `flock`. The deployment script uses a persistent lock file in `DEPLOY_PATH` to fail fast when another automated deployment or manual rollback is already running. The workflow validates that `DEPLOY_PATH` matches `/home/olvin/PROYECTOS/DevOps/applications/refuel-control`, creates it when absent, and refuses to use a symbolic link or a directory the runner service user cannot write.

Authenticate the server to GHCR once with a classic PAT scoped only to `read:packages`. Run this login as the same operating-system user that runs the GitHub Actions Runner service so Docker stores the credential in that user's profile:

```sh
read -r -s GHCR_PAT
printf '%s' "$GHCR_PAT" | docker login ghcr.io --username '<github-user>' --password-stdin
unset GHCR_PAT
```

Do not place this PAT in GitHub Actions and do not perform this login as a different user. Docker stores the server credential for subsequent `docker compose pull refuelcontrol-web` commands.

If the container package existed before this repository published it, open the package settings and grant this repository **Manage Actions access** with the **Admin** role. The cleanup action needs that relationship to retain four versions.

## Image traceability and identity

The `sha-<commit>` tag records which commit produced a package version, while `latest` identifies the newest publication. Tags are mutable registry pointers and are never used as the executable deployment identity. The build job captures the pushed image's `sha256:<64-hex>` OCI digest, and the deployment, verification, last-known-good state, and rollback all use `IMAGE_REPOSITORY@IMAGE_DIGEST`.

## Verify the deployed image

Run from `DEPLOY_PATH` on the server:

```sh
container_id=$(docker compose --env-file .env --file docker-compose.prod.yml ps -q refuelcontrol-web)
docker inspect --format 'configured_image={{.Config.Image}} image_id={{.Image}} health={{.State.Health.Status}}' "$container_id"
image_id=$(docker inspect --format '{{.Image}}' "$container_id")
docker image inspect --format 'oci_id={{.Id}} repo_digests={{json .RepoDigests}}' "$image_id"
curl --fail --silent --show-error https://refuelcontrol.fetek.es/healthz
curl --fail --silent --show-error https://refuelcontrol.fetek.es/ | grep -F '<app-root></app-root>'
```

`.Config.Image` must be `ghcr.io/renyb423/refuelcontrol@sha256:<64-hex>`, the OCI inspection must include that repository digest, health must be `healthy`, `/healthz` must return `ok`, and the root response must contain the Angular shell. `IMAGE_TAG=sha-<40-character-commit>` remains in `.env` only for traceability; `IMAGE_DIGEST` is the executable identity.

## Manual rollback

Rollback is possible only while the target digest belongs to a package version retained in GHCR. Obtain both the commit SHA and its exact `sha256:<64-hex>` digest from the retained GHCR package version or the corresponding workflow run. Pass the 40-character commit SHA without the `sha-` prefix:

```sh
bash ./deploy.sh ghcr.io/renyb423/refuelcontrol REPLACE_WITH_40_CHARACTER_COMMIT_SHA sha256:REPLACE_WITH_64_HEX_DIGEST
```

This uses the same lock, bounded health check, exact digest verification, and automatic recovery path as the workflow. The script records the traceability tag and executable digest in both `.env` and `.env.last-good`, and updates `.env.last-good` atomically only after the requested image is healthy and the Compose service state succeeds. A failed candidate restores `.env` from `.env.last-good` without changing the last-known-good state, and the script still returns failure after a successful automatic recovery.

## Server footprint

The GitHub-hosted build job uploads `refuelcontrol-deploy-bundle` with only `deploy/docker-compose.prod.yml` and `deploy/deploy.sh`. Their common `deploy/` prefix is removed by the artifact action, so the self-hosted job expects exactly `docker-compose.prod.yml` and `deploy.sh` at the downloaded artifact root and rejects any additional payload, non-regular file, or symbolic link.

The self-hosted job stages those files through `.next` paths, installs modes `0644` and `0700`, and atomically replaces each destination before invoking `deploy.sh`. The script maintains mode-`600` candidate state in `.env`, durable last-known-good state in `.env.last-good`, and a persistent `.deploy.lock` file. Application code, the Dockerfile, build credentials, and Supabase configuration files are never copied to the server.
